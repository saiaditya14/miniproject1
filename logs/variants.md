## Root causes found on Oct 7 (RTL read directly; evidence lives in logs/rtl_y16 and logs/rtl_r16c)
1. Correctness: tl_compute returned Ct as 512 scalar outputs wired straight from the fadd cores (`assign ap_return_0 = grp_fu_20702_p2;` in gemm_tl_compute8.v, fadd CE free-running outside its pipeline state, FSM goes state58 -> state1 unconditionally, `ap_done_reg` holds "done" but nothing holds the data). They were captured into depth-2 FIFOs (`Ct`) that the store pops only at its end; a store slower than compute fills them and the late capture takes garbage. Explains: RT=12/16 cosim zeroing the 4th/6th tile, RT=8 passing small cosim, RT=8 failing only the 4000-tile case on the card (HBM write jitter). Fix = Ct as a RAM channel (partition dim=2 only) with a row-by-row reduction in the compute epilogue. Verified in RTL (no ap_return, Ct_RAM PIPO) and in cosim (r16c).
2. Clock: the 189.8 MHz of v5b was one path in tl_store (the Ct mux). The Ct RAM change removes it. The next-worst path is unknown until v5bc / r16c16 report.
3. Loaders: with a dynamic row index into a completely partitioned At the loop drops to II=8 for more than 8 rows; the predicated store (`if (rr == r) At[rr][..] = v`) restores II=1.

## Operational notes
- slurm.sh hw uses --mem=32G --time=03:00:00 (OOMs in Vivado block synthesis for v5b-size designs); slurm.sh cosim has a 1 h limit (RT=16 with many tiles needs ~1.5 h). Use sbatch directly: hardware `--mem=96G --time=10:00:00`, cosim `--mem=32G --time=03:00:00`.
- Home quota is 20 GB. Each hardware build peaks at 3-5 GB and a full disk kills it ("Error writing message records"). Delete finished build/ folders; never delete a folder with a running job; never SFTP over a folder with a running job (a re-upload wiped a running cosim's log).
- Python quirks while generating variants: read the file BEFORE opening it with "w" (`open(p,"w").write(f(open(p).read()))` truncates first); `\n` inside bash heredoc python snippets can be collapsed, build backslashes with chr(92).
